# 把客户定制的模板公开出去

为一个客户做的海报流水线，往往是你手上最好复用的东西 —— 也最容易泄漏。
把两类产物分开：**生产流水线保持私有，公开的是去标识化副本**。
去标识化要在**第一次 push 之前**跑，不是之后。

## 必须扫两类语言

只扫客户名和中文业务词的扫描，**会漏掉英文措辞**。
实际漏出去的那句，通篇没有一个中文词、没有品牌名 ——
但它同时说出了一个**本机私有路径**和「这台机器上存在私有材料」这个事实。
（这句话本身不再引用于此，否则就是把泄漏又写了一遍。）
所以扫描表必须包含：

| 类别 | 例子 |
|---|---|
| 私有措辞（英文）| `client material`、`private pipeline`、`internal only`、`the user's real` |
| 绝对路径 | `/root/`、`/home/`、`/Users/`、`/opt/` |
| 工具缓存 | `.cache/`、`ms-playwright`、自建 venv 名、`.hermes` |
| 主机名 | `localhost`、`127.0.0.1`、`192.168.`、`.internal` |
| 客户业务词 | 用环境变量传，不要写死在脚本里 |

## 先标记，再人工过

正则扫描**一定会误报**：

- `~/.hermes/skills` 是**文档化的安装路径**，该留
- 仓库主的**用户名出现在 clone URL 里**，本来就公开
- 「换机构/换活动只改这一行」里的「机构」是通用词

所以扫描器的职责是**逼你逐条看一眼**，而不是替你下判断。
把「已确认误报」的理由写在报告里，下次才不用重想。

## 占位符要一眼看得出是占位符

| 写法 | 问题 |
|---|---|
| `示例科技` / `示例主讲人` / `示例市示例区` | ✅ 明显是假的，不可能撞名 |
| `云杉科技` / `林知远` | ❌ 看起来像真公司/真人，**重名风险和真名一样**，而且审阅时更难发现 |

## 四个我实际踩过的坑

### 1. 要改就得改**源头**，不要单独 patch 已发布的副本

公开副本是**衍生物**。你在副本上修好的字，下一次「同步」就被源文件覆盖回去了 ——
我因此把客户品牌名重新推上去过一次。顺序必须是：

```
改源 → 验源 → 重新同步 → 验副本 → 提交
```

不是：改副本 → 提交（下一次同步就回滚了）。

### 2. 扫的是**所有提交**，不是只有 HEAD

一个**只查当前工作区**的扫描完全不会发现历史里的东西。
历史里的文件在 `--force-push` 之后**依然能按 SHA 读到** —— 至少到 GitHub
垃圾回收之前。扫描命令带上每个提交：

```bash
for h in $(git log --format=%h); do git grep -lE "$PAT" "$h" -- . ; done
```

### 3. 用英文通用词扫描会大量误报

我在词表里加了 `trust`，结果每个提交都“命中 3 个文件” ——
实际是 `trusting a prior successful run`、`Don't trust automatic line breaking`。
差一点因此把一个干净的仓库删掉。
**误报和漏报一样危险**：漏报泄漏数据，误报让你做出错误的破坏性决定。
词表要写具体短语（`client material`），不要写单个常见单词。

### 4. 先看证据，再下结论

“5 个提交全中”和“零泄漏”我先后得出过这两个结论，两次都源于
同一个偷懒：看了计数，没看命中的**原文**。
每次判定前先把命中行打出来看一眼。

## 已 push 的泄漏，靠新提交修不掉

**旧提交在 `--force-push` 之后依然可以被 SHA 读到** —— GitHub 会保留
未被引用的对象，直到垃圾回收。处置顺序：

1. `git commit --amend`（或 rebase）把**当前树**改干净
2. `git push --force-with-lease` —— 线上文件立刻干净
3. 评估残留：内容只能被**知道那个 SHA 的人**读到。看泄漏性质决定要不要
   删库重建 —— **刚创建几分钟、没有 star/fork 的仓库，重建是便宜且彻底的**
4. 删库属于破坏性操作，先跟主人确认再动

每次对外同步前跑一遍。
