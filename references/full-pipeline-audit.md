# 全流程审计（Whole-pipeline sweep）

适用：用户说「全项目所有流程都跑到位」「看看有没有没发现的 BUG」「升级后全面验一下」。
目标不是「跑通几个脚本」，而是**逐个环节留下可复核的判据**，并把发现的缺陷分级。

审计自己也要有纪律：**一条通过记录的证据，不能是它自己的退出码经过管道后的样子。**

---

## 0. 先盘点，再跑

```bash
find <SKILL_DIR> -type f -not -path '*/.git/*' -not -path '*__pycache__*' | sort
ls -1 scripts/*.py | wc -l ; ls -1 references/*.md | wc -l
```

把文件清单当审计底稿：**每个 script 都要有对应环节、每个 reference 都要被引用到**。
先不知道有多少东西，就没法说「都跑到了」。

## 1. 退出码取法（整个审计的地基）

```bash
run() { local n="$1"; shift; "$@" >/tmp/rr.txt 2>&1; local rc=$?;
        printf "  %-28s RC=%-2d  %s\n" "$n" "$rc" "$(head -1 /tmp/rr.txt | cut -c1-52)"; }
```

- **禁止** `cmd | tail -n 20; echo $?` —— 那是 `tail` 的状态，命令失败也报 0。
- 需要看输出又需要真退出码：先重定向到文件再 `tail`，或 `${PIPESTATUS[0]}`。
- 判据：**参数错误应为 RC=2**（argparse 语义），**运行失败应为 RC=1**，**成功 RC=0**。
  三者混在一起说明错误处理没分层，本身就是一条要报的缺陷。

## 2. 环节清单（按依赖顺序，失败一次就停在这组）

### H. 边界输入
| 25 | 坏输入 | 0 字节文件 / 假 PNG / 1×1 / 不存在路径 | 必须 RC≠0；抛 Python 栈要记一条 UX 缺陷 |
| 25b | 跨平台一致性 | `build.ps1` vs `build.sh` 支持的格式集合 | 集合相同（注意 ps1 带 BOM，用 `grep -a`） |
| 25c | 仓库卫生 | `git status`、`check-ignore` 产物目录 | 工作区干净，产物/日志都被忽略 |

### I. 视觉抽查
| 26 | 接触表 | 全部版式拼一张，缩到 ≤1024 再送视觉 | 无空白 / 无重叠裁切 / 无豆腐块 / 无错位 |

> 视觉一次看 9 张会超时也会漏细节。拼图后**分两半看**，每半 3–5 张，问题描述按版式名逐条要。
>
> **超时是间歇的，不是尺寸的确定函数。** 同一张 1000×500 的图，第一次超时、原样重试就成功。
> 所以一次超时只够得出「重试」这一个结论：先原样重试，仍失败再拆更小或换局部。
> 把超时当成「图有问题」去重画，会白烧一次生成成本。「缩到 ≤1024 再送」是必要条件，不是充分条件。

## 3b-前置：交「修订建议文档」而不是直接改代码时

当要求「只出修订建议文档、由你本人改代码并上传」时，交付物形状固定：

- **开头一张清单表**：编号 / 严重度（P0 = 会让结果说谎，P1 = 影响可用，P2 = 只影响排错体验）/
  文件 / 一句话问题 / 是否实测。用户拿这张表决定先改哪条。
- **每条固定四段**：`位置`（文件 + 行号 + 函数名）→ `现状代码`（原样贴出，可搜索）→
  `问题`（现象 + 根因一句 + 为什么危险）→ `改为`（可直接粘贴的完整替代代码）→
  `验证`（改前/改后各一条命令 + 期望的 RC 与关键输出）。
- **已实测的条目打「✅实测」，并写明「在隔离副本上跑过」**；没验证过的绝不打标。
  验证在副本上做（`cp -r` 到 `/tmp`、改、跑、`rm -rf`），**全程不碰仓库工作区** ——
  `git status` 必须保持干净，用户才信你没偷偷改他的代码。
- **必带一节「不建议改的」**：列出看着像问题、实际是特性或有跨平台代价的地方
  （字体回退警告、坐标左闭右开、每次全量重渲的耗时）。用户拿到清单后最想顺手改的往往就是这些。
- **必带验收清单 + CHANGELOG 草稿**：改完逐条跑一遍（每条写出必须的 RC 值），CHANGELOG 直接可粘。
- 交付前对文档本身做一次隐私扫描：本机绝对路径、IP、机器 ID、key 前缀、仓库所有者名。
  这份文档会被用户拿去提问或贴进 commit，含本机路径就等于泄漏。

## 3. 这一趟真正会抓到什么（缺陷类型，不是个例）

- **参数键不校验**：枚举型参数（版式名 / 子命令）直接 `*) ONLY="$1"`，写错就静默走默认或全量。
  对照检查：同一脚本里**另一个**同型参数有没有校验 —— 不一致即是缺陷。
- **help 与实现不符**：help 说「名字或路径」，实现只 `os.path.isfile()`。凡 help 里出现「或」，
  都实际传两种形态各试一次。
- **会崩而不是会拒**：格式错抛 `ValueError` 栈并让调用方以为工具坏了。判据是「错参数应 RC=2 + 一句人话」。
- **孤儿文档**：新加 reference 忘了在 SKILL.md 里挂一行 —— 文件在、能力等于不存在。
- **指标本身是错的**：阈值硬编码（如「任一通道 < 245 就算墨」）让浅色/渐变版式报 99%。
  审计时**先用一张已知正常的成品反算这个指标**，指标与肉眼不符就要报，别拿它去判成品。
- **坐标系差一格**：numpy 切片左闭右开 vs Pillow 矩形含右边界，会凭空多报 1 行 + 1 列像素。
- **一次性修补脚本回流**：工作目录又出现 `fix*.py` / `p*.py` 就是「绕过工具层」的信号，
  与「禁止手写修补脚本」那条纪律直接冲突，必须报。

## 3b. 提修法之前先自证（最容易翻车的一步）

发现缺陷之后，**不要顺手写一个「看起来对」的修法就交出去**。同一处指标缺陷，先后给了三个
自认为合理的方案，全部实测失败：

| 想当然的修法 | 实测结果 |
|---|---|
| 判据改成「与四角背景色差 > 12」 | 有渐变/色块装饰的版式全跳到 99.8% |
| 判据改成「整图最高频量化色作背景」 | 白底 255 被量化到 240，差值直接超阈值 → 报 91% |
| 为了快把统计缩到 700px | 照片版从 60% 失真到 99% |

正解是**复用文件里已有的辅助函数**：同一文件上方 25 行就有一个取页面底色的函数，注释里明确写着
「不能写死白色」—— 作者造好了正确工具，只是坏掉的那个函数没调用它。

由此三条：

- **先搜再写。** 判「某函数判据错」之前，先在同一个文件里 grep 有没有现成的等价辅助函数
  （`grep -n 'def .*bg\|def .*color\|def .*sample\|def .*thresh'`）。
  作者常常已经修好了同一类问题的一半，另一半只是没接上。
- **任何修法必须在全部真实样本上跑一遍**（这里是 9 个版式），并把**改前 / 改后数字并排列出**。
  修法只要让别的样本变差，就不是修法。证据里要包含「为什么这条不会误伤」。
- **把排除掉的错误方案也写进文档。** 用户拿着文档去改代码，最容易顺手改成那个「看着更简洁」
  的错版本；一条「❌ 别改成 X，实测会让 6 个版式变 99%」能省掉一整轮返工。

## 4. 报告形状

1. **覆盖表**：环节 / 命令 / 结论（✅ ⚠️ ❌），一行一环节；跑不了的写 **SKIPPED + 原因**，
   不写「通过」。
2. **BUG 清单**，每条四件套：**复现命令** → 实际输出片段 → 根因一句话 → 建议修法（补丁片段）。
3. **分级**：P1 会让结果说谎（静默成功 / 验证环节崩 / 文档命令照抄必失败）；
   P2 只影响可读性与排错体验（栈、报错文案、指标噪声）。
4. 文档与注记可直接改；**涉及仓库代码的改动先出补丁供审阅**，不擅自推送 —— 审计者不该在
   审计过程中顺手改掉被审计的代码，否则「工作区干净」这条证据就没了。

## 5. 收尾（审计会自己污染环境）

- 删掉本轮生成的临时目录、接触表、测试图；`render_styles` 会往产物目录丢几十张 `style-*.png`。
- 真改图测试会产出 `*-diff.png`，别留在产物目录里。
- 最后再跑一次：`git status --porcelain` 应为空、`diff -rq 技能目录 仓库` 只剩**预期**差异
  （本机注记 / 运行时日志 / 本机补丁三样）。差异多出第四样，说明你改了什么没记录。

_审计的价值在于「每个结论都能被别人用同一条命令复现」。_
